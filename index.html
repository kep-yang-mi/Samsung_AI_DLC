01DEVELOPMENT WORKFLOW

코드보다 먼저, 계획을 검증한다

AI-DLC(AI-Driven Development Lifecycle)는 AI가 요구사항에서 테스트까지 이어서 작업하는 방식이다. 팀은 단계마다 방향을 검토하고, 승인한 내용을 다음 단계에 넘긴다.

WORKING SEQUENCE
01 / 04  ·  INCEPTION

팀이 먼저 문제를 정한다

사람
기획·개발·QA가 한 화면에서 목표와 제약을 합의한다.
AI
팀의 의도를 바탕으로 요구사항과 사용자 스토리를 제안한다.
남는 것
팀이 검토한 요구사항과 사용자 스토리
02 / 04  ·  PLAN REVIEW

코드를 쓰기 전에 계획을 검토한다

사람
설계 방향이 의도와 맞는지 확인하고 중요한 선택을 승인한다.
AI
요구사항을 설계와 작업 계획으로 구체화한다.
남는 것
승인된 계획과 그 결정을 내린 이유
03 / 04  ·  CONSTRUCTION

승인한 계획 안에서 구현한다

사람
각자 맡은 작업을 진행하며 코드와 테스트가 계획을 충족하는지 확인한다.
AI
앞 단계의 맥락을 이어받아 코드와 테스트를 생성한다.
남는 것
구현 코드, 테스트와 변경 제안(PR)
04 / 04  ·  APPROVAL

승인된 결과가 다음 일의 맥락이 된다

사람
GitHub PR에서 변경을 검토하고 승인한다.
AI
다음 작업에서 Second Brain에 쌓인 산출물과 결정 근거를 참조한다.
남는 것
병합된 산출물과 추적 가능한 승인 이력

속도보다 달라진 것

약 70% 단축은 대규모 신규 플랫폼을 기존 방식으로 개발할 때의 예상 일정과 비교한 결과다. 발표자는 회의가 줄고 담당자에 따른 결과 편차가 작아진 점을 더 의미 있는 변화로 꼽았다.

V2 전환: 도구가 바뀌어도 승인 기준은 같다

팀은 Kiro CLI나 Claude Code를 써도 같은 방법론과 승인 게이트를 거치도록 전환 중이다. V2는 5개 페이즈와 30개 이상의 스테이지로 세분화하며, AWS 원본 위에 팀 규칙과 서비스별 레거시 지식을 덧붙인다.

02CHANGE VERIFICATION

검증은 배포 뒤에도 계속된다

코드가 빨리 나와도 리뷰가 시작되기를 기다리는 시간은 줄지 않는다. 팀은 검증을 코드 리뷰 한 번에 맡기지 않고, 변경 전후의 서로 다른 신호를 확인한다.

GATE / 01머지 전

코드 변경을 테스트로

요구사항·UX 흐름·코드 변경을 바탕으로 Playwright E2E 테스트를 만든다. CI에서 회귀 테스트를 반복해 기존 흐름이 깨지지 않았는지 확인한다.

GATE / 02릴리스 시점

노출을 조금씩 늘린다

서버와 클라이언트의 피처 플래그로 기능을 켠다. 처음부터 전체에 공개하지 않고 1%, 10%, 50%처럼 대상을 단계적으로 늘린다.

GATE / 03릴리스 후

사용자 행동에서 확인한다

로그인 등 주요 흐름의 단계별 전환율을 평소 기준선과 비교한다. 테스트가 예상하지 못한 문제는 실제 사용자의 이탈로 드러날 수 있다.

이상 징후가 보이면노출 축소 또는 차단 → AI Ops가 원인 분석 → 다음 코드 변경에 반영
03PRODUCTION CONTROL

분석 권한과 변경 권한을 나눈다

에이전트는 로그와 지표를 읽고 계획이나 PR을 제안할 수 있다. 그러나 프로덕션에 직접 쓸 수는 없다. 사람의 승인을 받은 사전 정의 작업만 액션 컨트롤러가 실행한다.

INCIDENT NOTE / AWS REGION
약 3분

복구 시간이 아니라, 초기 판단 시간

리전 장애 당시 AI Ops가 여러 지표를 대조해 자체 코드보다 외부 리전 문제를 지목했다. 운영팀은 AWS 상태 페이지가 갱신되기 전에 준비해 둔 리전 전환 절차를 가동할 근거를 얻었다.

READ → CORRELATE → REPORT

운영 변경의 기본 승인 경로

전제: 에이전트의 프로덕션 직접 쓰기 금지

  1. 계획 PR · 에이전트가 요청을 분석해 변경 계획을 제안한다.
  2. 계획 승인 · 사람이 의도와 영향 범위를 검토한다.
  3. 실행 PR과 재승인 · 구체적인 작업을 별도의 변경으로 확인한다.
  4. 액션 컨트롤러 실행 · 미리 구현된 동작만 승인된 경로에서 수행한다.

파드 재시작처럼 정형화된 작업은 계획 단계를 생략할 수 있다. 버전 업그레이드처럼 복잡한 변경에는 전체 절차를 적용한다.

권한은 상속하지 않고 빌려준다

사용자 권한을 그대로 물려주지 않는다. 무권한 상태에서 시작해 작업에 필요한 도구와 시간만 허용하고, 호출 시점에 정책을 적용하며 감사 기록을 남긴다.

운영 분석은 함께 쓰는 도구로

Slack 알림을 받아 원인 후보를 회신하던 에이전트는 도메인별로 나뉘었다. 오케스트레이터가 요청을 분배하고, 각 도메인의 슈퍼바이저가 하위 에이전트의 결과를 종합한다.

04ORGANIZATIONAL MEMORY

결정의 이유를 다음 개발로 넘긴다

신규 구축과 달리 레거시에서는 코드만 읽어도 알 수 없는 제약이 있다. Second Brain은 “무엇을 바꿨나”뿐 아니라 “왜 이렇게 남겼나”를 찾아 다음 작업에 제공한다.

지식 정제 파이프라인 8단계
  1. 노이즈 제거
  2. 원자 단위 추출
  3. 엔터티 정리
  4. Relation 연결
  5. 중복·모순 처리
  6. 저장
  7. 정합성 검증
  8. 동기화

문서를 쌓는 것만으로는 충분하지 않다. 같은 대상을 가리키는 이름을 맞추고, 의존 관계를 연결한 뒤 서로 어긋나는 기록이 없는지 확인한다.

남겨야 할 지식의 예

폐기 예정 코드라도 오래된 클라이언트가 의존한다면 지울 수 없다. 코드 위치에 그 제약과 결정 이유를 연결해 두어야 다음 변경에서 같은 실수를 피한다.

근거가 충돌하면 충돌도 전달한다

장애 원인 질문에는 장애 회고를 우선하고, 접근 권한과 최신성을 확인한다. 서로 다른 기록의 결론이 다르면 하나를 임의로 고르지 않고 함께 넘긴다.

FIELD TAKEAWAY

첫 적용은 읽기 권한만으로 가치가 나는 일부터

알림을 읽고 원인 후보를 정리하는 일은 좋은 출발점이다. 다음 작업을 맡길 때는 아래 세 질문으로 위임 수준을 정한다. 검증할 수 있으면 게이트를 두고, 되돌릴 수 없는 일은 사람이 결정한다.
